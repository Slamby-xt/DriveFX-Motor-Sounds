# DriveFX Vercel, Neon, and Managed Payments migration

## Objective and baseline

Move DriveFX to the owner's COHEX Vercel team, store license and trial data in Neon Postgres, and use Stripe Managed Payments for paid checkout. Preserve the existing static cockpit, audio, GPS and simulated driving, garage, free trial and Pro UI, phone QR flow, device IDs, and admin panel. Keep the canonical URL at https://drivefx.pro and the existing path-preserving redirect from www.

The prior architecture served the static build and same-origin license API on Vercel and used Upstash for storage. Reuse the Vercel entry points and public asset allowlist while replacing the Upstash dependency with Neon Postgres. The Cloudflare implementation remains historical. This pre-launch migration starts with a fresh database. Confirm control of the domain assignment before deployment to the owner’s team or any DNS change.

## Interfaces and storage

Keep the existing public routes and response shapes for status, trial, prices, checkout, confirmation and billing, plus the admin grant, extend, revoke, list, email lookup and relink operations. Keep the Stripe webhook at /stripe-webhook. Retain the five free cars, the five-minute trial, local browser identity and offline behavior, the paid-period grace interval, and existing units and settings. Publish only the existing site assets and API routes. Keep Stripe secrets, database credentials, admin credentials and raw payment or trial data out of browser bundles and logs. Keep the server-side admin token, authenticated routes, and bounded per-network rate limit. Use Vercel-managed IP and country inputs for their appropriate routing, rate-limiting and currency hints.

Add a versioned SQL migration for Postgres. Use a server-only, least-privilege application role and a serverless-compatible transaction pooler. Provide an isolated production database and a separate test database in the release plan. Document how to apply the migration, create or grant the runtime role, configure several environments without leaking secrets, and verify the runtime role has access only to its required application data. Runtime keys and privacy-sensitive trial identifiers must be protected. Expire transient counters and trial records consistently with the existing retention policy. The public Data API must have no access to this data.

Store device entitlements, Stripe customer and exact purchase mappings, processed webhook IDs, trial usage, and short-lived counters. Reuse the existing store interface if that preserves correct transactions and simplifies the change. Use database transactions and uniqueness for entitlement updates, exact purchase claims, and webhook deduplication. The event outcome and its processed marker must commit together, and temporary failures must be retryable. Network calls to Stripe should be bounded and outside data locks where feasible. Handle duplicate and reordered webhooks and defend against stale state overwriting a newer entitlement. Ensure concurrent renewals cannot downgrade Lifetime, and that simultaneous trial updates keep the larger recorded usage. Transactions must cover manual relink and applicable purchase mapping changes.

## Payments

Use the dedicated DriveFX live Stripe account, separate from Cohex. Its live catalogue already contains the three active tax-inclusive prices below. The original DriveFX sandbox under Cohex has legacy test products. Use the newer sandbox under the dedicated DriveFX account for staging. It starts with an empty catalogue. Use compatible test products, tax category, prices, webhook, and portal for testing. Reconcile any changes to the repository's provisioning scripts so a rerun can recognise existing lookup keys and the Dashboard-created Monthly product rather than duplicating it. Reuse the existing approved live catalogue during launch. Do not create live subscriptions, charges, payment links, products or a live webhook while implementing this PR.

Reuse a compatible open Checkout Session or another bounded persistent idempotency mechanism across duplicate browser or QR attempts. Document a recovery path for duplicate completed charges without issuing automatic refunds during this PR.

**Production sales gate.** Leave sales disabled by default while license status, the admin panel, the portal where configured and the webhook continue to work. The owner wants paid sales only where Stripe assumes indirect tax responsibility. Stripe documents a [Radar billing-country block rule](https://support.stripe.com/questions/block-payments-from-tax-unsupported-countries-using-radar?locale=en-GB) for Managed Payments. Use Stripe's current covered-market list for this UK seller and reject missing or unsupported billing countries. Radar Plus or Pro requires separate approval because it adds cost. Verify a supported and an unsupported billing country end to end in the sandbox, including enabled payment methods and subscription renewals, before public sales. IP location can suggest currency but does not establish the checkout tax location. Stripe documents that a Managed Payments transaction can still occur outside its tax coverage. If the Radar policy cannot be approved, applied and verified, keep live checkout closed and state the launch blocker in the PR and rollout documentation. Do not assert worldwide tax coverage. Keep the agreed price behavior and the separate production enablement step visible in the runbook.

See [updating Checkout for Managed Payments](https://docs.stripe.com/payments/managed-payments/update-checkout), [tax coverage](https://docs.stripe.com/payments/managed-payments/tax-compliance), [webhook verification](https://docs.stripe.com/webhooks), and [Neon connection pooling](https://neon.com/docs/connect/connection-pooling).
